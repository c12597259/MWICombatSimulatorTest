# Rust 触发条件预解析与列表复用实验

日期：2026-10-04。基线为 `codex/rust-wasm-migration` 的 `182d7ec`，已包含怪物基础属性缓存与 buff 类型索引。本轮只修改 Rust，保持战斗规则、浮点计算和随机数调用顺序。

## 两个候选

**条件预解析**：反序列化触发器时，把依赖对象、条件和比较器解析为内部枚举。buff 条件直接引用静态完整键，避免执行时重复拆分字符串、匹配条件名和拼接 buff 键。JSON 输入输出字段保持原样；未知标识仍延迟到实际求值时报告错误，保留冷却、控制状态和缺少目标时的跳过行为。条件为假后仍继续求值其余条件。

**列表复用**：每次检查消耗品时，不再克隆双方队列并创建新的存活单位列表，而是复用一个 `Vec<UnitId>`。仍按玩家、敌人的顺序，分别固定当时的存活单位快照，保留连续消费直到稳定的循环。成功和错误返回都清空快照并归还容量，不保留历史单位引用。

## 回归验证

- 1,191 个冻结 JS 战斗场景、12,953 帧逐事件记录在 native/WASM 两端通过对照。其中 840 个触发器场景覆盖条件、依赖和比较器矩阵；机制用例包括连续消耗品观察前一次恢复及 buff、稀疏技能槽、低蓝跳过和双方存活/死亡单位聚合。
- 完整战斗回归 56 项、专精护符对照 6 项通过，包含 24 小时地下城日志和 72 小时普通地图内存回收。
- Rust 单元测试 17 项通过。新增覆盖 JSON 形状与默认值、未知条件的延迟报错、冷却/控制/目标跳过、假条件后继续求值，以及错误后归还列表容量和队伍变化后不残留引用。
- 格式化及 workspace/all-targets Clippy（warnings 视为错误）通过。
- 最终恢复的源码与已测试合并版本逐字节一致，重新编译后的 WASM SHA-256 也与正式矩阵中的合并版本一致。

## 计时方法

使用此前重建的 11 个三人队伍配置，每次模拟 24 小时、种子 7。Edge 154.0.4258.37 的实际 WASM Worker 串行执行，计时包含模拟、结果序列化及 JSON 解析，不含模块初始化、结果哈希和 Playwright 回传。

初筛运行三个版本，共 132 次，出现明显的启动阶段计时波动；其合并总降幅约 7.9%，不作为最终结论。随后增加“仅列表复用”版本，重新运行完整四版本矩阵：每版本、每配置预热一次，正式计时四次，轮换顺序，使每个版本在四个位置各运行一次。

正式矩阵共 220 次运行（44 次预热、176 次计时）。每次核对完整结果哈希、随机数调用次数、事件总数及各类型事件数，并与此前 JS 的结果哈希和随机调用次数比较；全部一致。只排除日志中的现实时间戳。

这些是固定重建输入的新对照，不是原始导出历史的随机战斗回放。原始输入、版本源码和产物、逐轮计时及本机脚本都保存在忽略目录 `.bench/rust-triggers-stage3/`，不提交、不上传。

## 后续采样与下一方向

正式计时后，对合并版本的三个配置分别预热一次、采样两次，CDP 间隔 1 ms，剔除 idle 样本。这些运行不计入正式成绩，九次结果检查均通过。

| 函数 | 巫师之塔 T4 | 地狱深渊 T3 | 魔像洞穴 T3 |
| --- | ---: | ---: | ---: |
| 消耗品触发流程（含子调用） | 16.0% | 17.6% | 16.9% |
| should_trigger（含子调用） | 2.2% | 2.9% | 2.7% |
| 属性重算（含子调用） | 15.7% | 19.2% | 20.4% |
| JSON IndexMap 键查询（自身） | 10.0% | 7.6% | 4.9% |
| malloc（自身） | 8.1% | 8.5% | 8.2% |

包含子调用的占比会重叠，编译器内联和采样时的运行状态也会影响归属，不能相加或直接解释成可节省时间。上一阶段采样中触发流程约占 19.5%～22.0%，should_trigger 约占 5.3%～5.8%；本轮条件求值占比下降，但触发流程还有其他成本。

本轮 `str::Pattern::is_contained_in` 与 `StrSearcher::new` 两个自身样本合计约占 8.1%～10.8%；按最近的模拟器调用栈归属，其中约 96%～100% 落在 `check_triggers`。源码中该循环在冷却判断前执行 `item.category.contains("food")`，实际消耗时还会判断 `drink`/`food`。下一阶段优先单独测试在消耗品初始化时保存这两个分类结果，保留原来的子串匹配语义，避免把可同时匹配两者的输入错误地改成互斥枚举。

另一个方向是结果统计的 JSON 操作：最近模拟器调用者为 `result::increment` 的样本占上述 JSON 键查询的约 41%～56%。因此后续需要区分结果累计与游戏定义查询，不能把所有 JSON 查找都归因于定义表。先做消耗品分类的小范围对照，再考虑固定统计字段的结构化累计与重复对象分配。
