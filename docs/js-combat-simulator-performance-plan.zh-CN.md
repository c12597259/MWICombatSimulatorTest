# 战斗模拟器 JavaScript 性能优化计划

更新时间：2026-09-21  
状态：首轮实现与自动回归完成；剩余页面冒烟检查待补  
范围：先优化现有 JavaScript 战斗内核；本计划不包含 Rust/WASM 重写。

## 执行结论（优先于下文原始方案）

详细实测见 [首轮优化报告](js-combat-simulator-performance-results.zh-CN.md)，复现方法见 [bench/README.md](../bench/README.md)。

- 72 小时 d4T2 固定种子测试：优化前中位数 329.13 秒，优化后 40.73 秒，约 8.08 倍；本地浏览器单次 33.59 秒。测试期间有其他任务并发，用时存在波动，不作为严格隔离的性能承诺。
- 三次完整运行及六个短场景：新旧完整战斗结果一致（仅剔除团灭记录的现实时间戳），随机数调用次数一致。
- 实际首要热点是反复计算装备基础属性、反复筛选增益和标准化神龛等级，已加入适当作用域的缓存。移除逐事件异步、限制进度通信、默认关闭战斗日志也已完成。
- 事件队列只消除无用复制，保留原堆删除与同时间事件顺序。原提案的索引/延迟删除暂不实施，避免改变模拟结果；并未宣称它仍是最大热点。
- 随机种子只在独立 Node 基准进程中注入，没有改变正式页面的随机算法或历史记录格式。
- 批量地图/迷宫使用有界 Worker 池；计划模拟是历史数据汇总，本身没有战斗计算，不增加无用的并行机制。
- 独立生产构建已完成，保留用户脚本的 Tampermonkey 元数据。现有 64 项与新增 11 项自动测试通过。
- 内置浏览器已完成五人 d4T2 的导入、72 小时模拟及结果检查；连接随后不可用，全图/迷宫/历史/计划页面的完整交互冒烟尚未完成。相关核心和数据逻辑已做自动测试，但不替代页面检查。
- 地下城换波准确性仍需游戏实测证据，不随本轮性能变更修改。Metz 的结果不是正确性基准；不能为对齐它的 DPS 而直接改战斗规则。
- 当前先保留 JS 方案，不启动 WASM 重写。没有证据证明 39 秒就是 JS 上限。

下文保留最初的阶段设计；未实施部分不视为本轮已完成。

## 1. 背景与目标

当前固定对照案例：

- 输入：`d4T2.txt` 五人测试队伍
- 区域：海盗基地（T2）
- 模拟时长：72 小时
- 当前模拟器实测：约 392 秒
- Metz 模拟器实测：约 4～5 秒
- Metz 对照结果：完成 42 次、团灭 1 次

392 秒与 4～5 秒之间不是单靠增加 Worker 就能消除的差距。当前已确认的主要性能嫌疑包括：

1. `CombatSimulator.simulate()` 每处理一个事件都会 `await this.processEvent(...)`，但 `processEvent()` 内没有真正的异步操作。
2. `EventQueue` 的查询和删除会反复执行 `Heap.toArray()`，再逐项搜索或从堆中删除。
3. 热路径里存在较多临时数组、对象和高频进度消息，可能造成垃圾回收和线程通信开销。
4. 批量模拟会为每个任务重新创建和销毁 Worker；不过这不影响单个 72 小时模拟的核心速度。

本轮优化目标分三级，均以同一设备、同一浏览器、同一测试数据的预热后中位数为准：

| 目标 | 72 小时 d4T2 用时 | 含义 |
| --- | ---: | --- |
| 最低目标 | 不高于 196 秒 | 至少 2 倍加速，确认 JS 优化路线有效 |
| 理想目标 | 不高于 78 秒 | 至少 5 倍加速，日常使用明显改善 |
| 进取目标 | 不高于 39 秒 | 至少 10 倍加速，作为阶段目标而非 JS 架构上限 |

这些数值是阶段目标，不是预先保证。若完成事件队列和热路径优化后仍明显高于 39～78 秒，再评估 WASM，而不是为了追逐 4 秒继续堆叠高风险 JS 改动。

## 2. 基本原则

### 2.1 性能改动与规则改动分离

纯性能提交必须在相同随机种子下保持结果一致。以下内容属于准确性修正，必须独立提交、独立验收：

- 地下城换波时是否保留玩家攻击计时；
- 地下城换波时是否允许正在进行的技能施法完成；
- 换波间隔及其随机分布；
- 其他与 Metz 或游戏实测不一致的战斗规则。

目前已经发现我们的地下城换波会清除普攻事件，并在新一波开始时清除施法完成事件；这是否解释 d4T2 的人物 DPS 差异仍是假设，尚无游戏实测证据，不属于本轮性能优化。

### 2.2 每项优化必须可测量、可回退

- 每个阶段单独提交。
- 每个阶段执行相同的基准测试。
- 记录运行时间、事件数量、内存峰值和关键结果。
- 若一次复杂优化的中位数收益低于 5%，原则上回退，除非它明显简化了后续工作。
- 不用一次大重构同时修改事件队列、随机数和战斗规则。

### 2.3 不用多线程掩盖单线程热点

单个 72 小时模拟本质上是一条有状态时间线。把它强行拆成多个短模拟会重置生命、法力、冷却、地下城波次和随机状态，无法与原结果严格等价。

Worker 池适合：

- 同时模拟多个地图；
- 计划模拟中的多个历史方案；
- 多个独立随机种子的统计模拟。

Worker 池不作为单个 d4T2 模拟的第一阶段解决方案。

## 3. 阶段 0：建立可重复基准

这是所有代码优化之前的必做项。

### 3.1 基准运行器

新增一个不依赖页面操作的基准入口，复用正式的角色解析、区域构造和战斗内核。至少支持：

- 指定队伍 JSON；
- 指定地图、难度和模拟时长；
- 指定随机种子；
- 开关 HP/MP 时序记录；
- 输出机器可读的 JSON 报告；
- 输出 wall-clock 时间和事件统计。

浏览器端最终仍需做一次端到端验证，但日常性能迭代优先使用无 UI 基准，避免渲染、DevTools 和标签页状态影响结果。

### 3.2 可注入随机数生成器

战斗内核当前直接调用 `Math.random()`。需要把战斗相关随机数统一收口到可注入的 RNG：

- 正常使用时自动生成种子；
- 基准测试时使用固定种子；
- 历史记录可选保存种子，便于复现；
- 页面 ID 等非战斗随机数不纳入战斗 RNG。

第一版只替换战斗模块中的随机调用，不同时改变随机算法之外的规则。

### 3.3 基准指标

每次至少记录：

- 总用时；
- 总处理事件数及各事件类型数量；
- 事件队列最大长度；
- `getMatching`、`clearMatching`、`contains...` 的调用次数和扫描条目数；
- 进度消息数量；
- 完成次数、团灭次数和 eph；
- 每名角色的总伤害、DPS、死亡次数、经验、消耗品；
- 期望掉落；
- 如环境允许，记录峰值堆内存和垃圾回收占比。

### 3.4 基准矩阵

除 d4T2 外，再保留几组较短的覆盖案例：

1. 单角色普通地图；
2. 三角色普通地图；
3. 五角色地下城；
4. 高频团灭地下城；
5. 含眩晕、沉默、致盲、持续伤害和复活的队伍；
6. 迷宫；
7. HP/MP 时序记录开启与关闭。

验收条件：固定种子连续运行得到一致的关键结果；基准本身不改变正式模拟结果。

## 4. 阶段 1：低风险热路径优化

### 4.1 移除逐事件 Promise 开销

修改方向：

- 将 `processEvent()` 改为同步函数；
- 在主循环中直接调用，不再逐事件 `await`；
- `simulate()` 暂时可以保留 Promise 接口，避免改动 Worker 和调用方接口；
- 不改变事件处理顺序。

这是最先执行的代码优化，因为改动小、结果容易校验，并且当前每个事件都会付出一次不必要的异步开销。

### 4.2 限制进度通信频率

当前每 1000 个事件派发一次进度消息。调整为：

- 普通模拟最多每 200～250 毫秒发送一次；
- 同时保证进度百分比有最低变化量；
- 完成时始终发送 100%；
- HP/MP 时序采样与 UI 进度消息解耦，避免为了减少消息而丢失图表采样。

### 4.3 关闭非必要热路径日志

- 默认不在长模拟中打印每次团灭和波次日志；
- 增加明确的 debug 开关；
- 错误和最终摘要仍保留。

### 4.4 验收

- 相同种子下关键结果完全一致；
- 页面进度条仍会更新，且模拟结束时为 100%；
- 记录该阶段相对基线的加速比。

## 5. 阶段 2：重构事件队列

原方案把它列为主要候选热点；实际分析表明重复属性计算收益更大，队列的大规模重构已暂缓。

### 5.1 当前问题

当前 `EventQueue`：

- 查询时将整个堆复制成数组；
- `clearMatching()` 遍历数组后逐个调用堆删除；
- 击杀、控制效果、团灭和换波都会频繁触发这些操作；
- 任意 predicate 接口让索引无法有效发挥作用。

### 5.2 目标结构

采用“最小堆 + 索引 + 延迟删除”：

- 最小堆继续负责按时间取下一个事件；
- 事件增加内部 ID 和 `cancelled` 状态；
- 取消事件时只标记并从辅助索引注销，不立即在堆中间删除；
- `getNextEvent()` 弹出并跳过已取消事件；
- 当已取消事件比例过高时再一次性压缩堆；
- 维护按类型、来源单位、目标单位和 HRID 的索引集合。

### 5.3 用明确 API 替换任意 predicate

逐步将以下通用调用：

- `getMatching(fn)`
- `clearMatching(fn)`

替换为可索引的明确操作，例如：

- `hasType(type)`
- `hasTypeForHrid(type, hrid)`
- `findForSource(types, source)`
- `cancelType(type)`
- `cancelForUnit(unit)`
- `cancelTypeForSource(type, source)`
- `cancelTypesForSource(types, source)`

只有极少数确实无法索引的查询才保留慢速路径，并在基准中计数。

### 5.4 正确性风险

重点验证：

- 同一时间戳的事件顺序不能无意改变；
- 取消后不能从辅助索引中残留；
- 已取消事件不能再次执行；
- 事件对象不能被复用后错误命中旧索引；
- 大量延迟删除事件不能无限占用内存；
- 眩晕、致盲、沉默、诅咒、狂怒、虚弱和复活的覆盖/刷新逻辑保持一致。

阶段 2 应先补事件队列单元测试，再替换正式实现。

## 6. 阶段 3：减少热路径分配和重复计算

本阶段只处理性能分析明确指出的热点，不进行盲目微优化。

候选项：

- 将高频 `filter()`、`map()`、`reduce()`、数组展开改为单次循环；
- 避免每个遭遇或每次攻击创建不必要的临时数组；
- 缓存不随战斗变化的 HRID、单位列表和静态属性；
- 避免重复读取深层对象路径；
- 评估事件对象池，但仅在 GC 确认为主要瓶颈时实施；
- 评估将字符串事件类型改为整数枚举，但仅在收益可测且调试体验可接受时实施；
- HP/MP 可视化关闭时，不创建任何相关快照或消息数据。

不应过早引入 TypedArray 或大规模数据布局重写；这类改动接近重写内核，风险与 WASM 迁移相近。

## 7. 阶段 4：Worker 与批量任务优化

在单次模拟内核稳定后再处理：

- 建立可复用 Worker 池；
- 批量地图和迷宫任务完成后不立即销毁 Worker；
- Worker 数量使用 `hardwareConcurrency - 1`，至少保留一个线程给页面；
- 限制低内存设备的最大 Worker 数；
- 避免每个任务重复传输不变的游戏数据；
- 对大对象评估 transferable 或 Worker 内缓存；
- 计划模拟优先把互相独立的步骤并行执行。

验收重点是批量总耗时、页面响应性和内存峰值。它不会作为单个 d4T2 模拟的加速数字。

## 8. 阶段 5：构建与部署优化

当前 webpack 配置使用 `mode: "development"`。正式部署应增加独立的生产构建：

- 本地开发继续保留 source map 和易读代码；
- GitHub Pages 使用 production 模式；
- 生产构建关闭不必要的调试代码；
- 对比构建大小、加载时间和实际模拟时间；
- 不把压缩后的包体变小误认为战斗内核已经显著加速。

该阶段主要改善下载、解析和启动速度，预计不会单独解决 392 秒的核心问题。

## 9. 独立准确性任务：地下城换波

完成至少阶段 0 后，单独处理以下问题：

1. 普通地图换怪是否取消正在进行的施法；
2. 地下城换波是否保留玩家普攻剩余时间；
3. 地下城换波是否允许正在进行的施法完成；
4. 敌方攻击事件在换波时如何清理；
5. 控制效果、持续伤害、增益和冷却是否跨波保留；
6. 有规则证据后重新比较 d4T2 的五人 DPS、完成和团灭次数；不把 Metz 的 42 次完成、1 次团灭当作必须匹配的目标。

这一任务预期会改变模拟结果，所以不能用“结果必须完全一致”的性能验收标准，而要依据游戏实测或可信的规则记录验收。

## 10. 每阶段执行流程

每个优化阶段按同一顺序执行：

1. 在修改前运行三次预热和至少三次正式基准；
2. 保存中位数、最小值和最大值；
3. 只实施一个可解释的改动；
4. 运行单元测试和构建；
5. 使用固定种子比较完整结果 JSON；
6. 重跑基准并计算加速比；
7. 用浏览器页面做一次实际操作验证；
8. 更新性能记录；
9. 达不到收益或破坏结果则回退该改动。

建议提交顺序：

1. `perf: add deterministic combat benchmark`
2. `perf: remove per-event async boundary`
3. `perf: throttle worker progress messages`
4. `perf: add indexed lazy-cancel event queue`
5. `perf: reduce allocations in confirmed hot paths`
6. `perf: reuse workers for batch simulations`
7. `build: add production deployment build`
8. `fix: preserve dungeon player timelines between waves`（准确性，独立于性能提交）

## 11. 是否转向 WASM 的决策点

完成阶段 1～3 后再决定：

- 若 d4T2 已进入 39～78 秒范围，优先继续维护 JS 版本；
- 若仍高于约 120 秒，且分析显示主要时间已消耗在大量数值运算而不是明显的数据结构问题，应停止高风险微优化，评估 Rust/WASM；
- 若目标明确要求接近 Metz 的 4～5 秒，应把 WASM 视为单独项目，而不是本计划的隐藏追加项。

WASM 迁移前必须保留本计划建立的固定种子、黄金结果和基准矩阵，否则无法验证新旧内核是否等价。

## 12. 完成定义

本 JS 优化计划完成需要同时满足：

- 基准运行器可重复运行；
- 固定种子下，纯性能改动不改变关键模拟结果；
- 所有现有测试通过；
- 新增事件队列和确定性随机测试通过；
- `npm run build` 成功；
- d4T2 的最终中位时间、加速比和环境信息已记录；
- 页面单图、全图、迷宫、计划模拟和 HP/MP 图表均完成冒烟测试；
- 地下城换波准确性修正有独立结果记录；
- 是否继续 WASM 已根据实测数据作出决定。
